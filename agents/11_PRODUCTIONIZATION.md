# 11 — Productionization

The goal of this file: make the trained policy something a company could
plausibly deploy, not just a checkpoint in a notebook. Because our actor
network is tiny (`[256,256]` MLP, `05_RL_ALGORITHM_SPEC.md` §1), the
production story is unusually clean — this is worth stating explicitly in
the final write-up as a deliberate design outcome, not an afterthought.

## 1. Export

`python/export/export_onnx.py`:

1. Load the trained SAC actor checkpoint (best condition from
   `10_EXPERIMENTS_AND_EVALUATION.md`, or a specific one selected by the
   user).
2. Export the **deterministic mean action** path only (i.e. $\mu(x)$ after
   the tanh squash, not the stochastic sampling path — a deployed
   controller should be deterministic given a state, exploration noise is
   a training-time device only).
3. `torch.onnx.export(...)` with fixed input shape `(1, state_dim)`,
   opset version pinned and recorded in `results/export/manifest.json`.
4. **Parity check**: run the same input through the PyTorch model and
   through `onnxruntime.InferenceSession` on the exported graph; assert
   outputs match to a small numerical tolerance (e.g. `1e-5`). Fail the
   export step (don't ship) if parity fails.

## 2. Rust inference server (`rust/inference_server/`)

- Crate: `ort` (`03_EXISTING_REPOS_TO_CLONE.md`) for ONNX Runtime, `axum`
  for the HTTP surface, `serde`/`serde_json` for (de)serialization.
- **No PyTorch, no CUDA, no Python dependency at runtime.** The server's
  only artifact dependency is `policy.onnx` plus a small `manifest.json`
  describing input/output tensor names, shapes, and the state-vector
  field order (must exactly match `04_MATH_SPEC.md` §1's state definition
  — this manifest is the contract between the Python training side and
  the Rust serving side, and should be generated automatically by the
  export step, never hand-written, to prevent drift).
- CPU execution provider by default (a 256-256-22 MLP runs in well under a
  millisecond on CPU — there is no reason to require a GPU, or even a
  specific one, at the deployment edge; this is worth calling out as a
  deliberate advantage of keeping the RL networks small per the hardware
  constraints in `02_TECH_STACK.md`, not just a workaround for them).

### API contract (sketch)

```text
POST /v1/act
  body: { "state": [f32; STATE_DIM] }
  response: { "action": [f32; ACTION_DIM], "latency_us": u64 }

GET /v1/health
  response: { "model_version": "...", "state_dim": N, "action_dim": 22 }
```

- Validate incoming `state` length against the loaded manifest; reject
  malformed requests with a clear error rather than silently truncating
  or padding.
- Latency budget: p99 well under the control-loop period implied by the
  50 Hz control rate (`06_ROBOT_AND_SIMULATION_SPEC.md` §2), i.e. under
  ~20ms, with a target of low-single-digit milliseconds given the network
  size — measure and record this, don't just assert it.

## 3. Testing

- `tests/rust/inference_server_parity.rs`: load a handful of
  (state, expected_action) pairs generated by the Python parity check
  (§1) and assert the Rust server reproduces them.
- Basic load test (e.g. `k6`/`wrk` or a simple Rust benchmark) to confirm
  the p99 latency budget holds under a realistic request rate (a single
  robot's control loop calling once per control period, plus headroom for
  local development/testing traffic).

## 4. Versioning

- `policy.onnx` filenames include the git commit and experiment id, e.g.
  `policy_condition-e_<gitsha>.onnx`, matching the reproducibility
  manifest in `10_EXPERIMENTS_AND_EVALUATION.md` §5, so a served model can
  always be traced back to the exact training run and config that
  produced it.

## 5. Explicitly out of scope for this project (document, don't build)

- Real-robot deployment / sim-to-real transfer — no physical Allegro hand
  is assumed to exist for this project; the "production" story here is
  "a real robot controller *could* call this API," validated by the
  parity and latency tests above, not an actual hardware integration.
- Multi-model serving, auth, rate limiting, and other general API-gateway
  concerns — a single-binary, single-model server is the right scope
  here; note in the write-up that these would be the obvious next layer
  for a real deployment, without building them speculatively.
